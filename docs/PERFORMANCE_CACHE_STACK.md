# Caches et préremplissage CUDA

Les optimisations de l'[épique #98](https://github.com/azerothl/Rbitnet/issues/98) sont activées séparément. Les poids quantifiés et les experts sélectionnés par le routeur restent ceux du GGUF. Le placement fixe et les chemins CPU restent les références de comparaison.

## Options expérimentales

| Option | Effet et limites |
|---|---|
| `RBITNET_PREFIX_KV=1` | Llama, GPT-OSS résident et MLA résident réutilisent les K/V du préfixe commun en recalculant le dernier token. Qwen3.5 conserve des checkpoints complets : K/V des blocs d'attention, état GDN et historique de convolution. |
| `RBITNET_CUDA_PREFIX_MB=256` | Budget des snapshots par runtime, en MiB. Il inclut les états CPU et GPU Qwen. Les poids et le KV actif ont leurs propres allocations. |
| `RBITNET_CUDA_PREFIX_ENTRIES=16` | Nombre maximal de snapshots ; éviction LRU avant allocation. |
| `RBITNET_PREFIX_KV_MIN_TOKENS=8` | Longueur minimale réutilisable. Llama recalcule toujours le dernier token pour obtenir ses logits. |
| `RBITNET_QWEN_PREFIX_CHECKPOINT_TOKENS=256` | Intervalle des checkpoints Qwen pendant le préremplissage. L'état récurrent ne peut pas être tronqué à un préfixe arbitraire. |
| `RBITNET_MOE_CACHE_MB=4096` | Cache GPU par expert pour GPT-OSS et GLM/deepseek2. `0` garde le placement fixe. Gate/up/down sont chargés ensemble, sans conversion. |
| `RBITNET_MOE_CACHE_POLICY=lru` | Politique `lru`, `lfu` ou `least-stale`. LRU reste la référence ; les autres politiques peuvent être plus lentes. |
| `RBITNET_MOE_EXECUTION=cache` | Politique routée GPT-OSS/MLA : `cache` conserve le comportement précédent ; `cpu` calcule les projections d'experts via SIMD CPU et évite de placer leurs banques/cache en VRAM ; `adaptive` compare le coût CPU au coût GPU + chargements manquants, par couche, avec calibration et sondes périodiques. Les normes/attention/tête et FFN partagés gardent leur placement. Expérimental : décision sur le FFN routé complet, sans exécution mixte par expert ni recouvrement de copies. GPT utilise les segments pour `cpu`/`adaptive`. |
| `RBITNET_CUDA_DEVICE_BUDGET_MB=12288` | Plafond commun des allocations CUDA gérées dans le processus : poids, experts, KV/états, activations, snapshots et scratch. Nouvelle ABI requise, option désactivée par défaut. GPT-OSS/GLM réservent leurs états avant le placement des poids ; Llama/Qwen sont plafonnés mais cette priorité au chargement reste à intégrer. |
| `RBITNET_CUDA_DEVICE_MARGIN_MB=256` | Marge libre supplémentaire sur le GPU au chargement. La limite effective tient compte des allocations gérées déjà vivantes et de la mémoire libre actuelle ; elle ne peut pas augmenter tant que des allocations restent actives. |
| `RBITNET_MOE_TRACE_DIR=...` | Trace JSONL du routage réel. Désactiver pour mesurer les performances sans coût de journalisation. |
| `RBITNET_CUDA_PREFILL=1` | Préremplissage Llama par blocs : GEMM quantifié SIMT, attention causale, résidus et FFN sur GPU. Désactivé par défaut. |
| `RBITNET_CUDA_PREFILL_TOKENS=128` | Taille du bloc, bornée entre 1 et 128. Les projections partagent les tuiles de poids décodées entre tokens ; les poids complets ne sont pas déquantifiés en F32. |
| `RBITNET_CUDA_PREFILL_TF32X3=1` | Projections Llama ou Qwen dense par Tensor Cores compensés sur SM80+, avec leur option de préremplissage par blocs. Trois produits TF32, sous-totaux additionnés en FP32 ; huit formats GGUF conservés. Blocs d'au moins 64 tokens, au moins 1 024 colonnes et 131 072 éléments de sortie ; les petites projections restent SIMT. Option expérimentale, précision proche du F32 et non bit-exacte. |
| `RBITNET_CUDA_QWEN_FULL=1` | Pipeline Qwen3.5 dense entièrement résident pour `cuda`, contexte maximal 8 192 : attention complète, blocs GDN, FFN et sortie sur un flux. Une entrée d'embedding et une position sont transférées par token ; seuls les logits ou l'ID glouton reviennent sur CPU. |
| `RBITNET_CUDA_QWEN_FULL_GRAPH=0` | Désactive le graphe de ce pipeline pour vérifier le chemin eager. Les activations restent sur GPU. |
| `RBITNET_CUDA_GPT_FULL=1` | Attention/KV GPT-OSS, routeur et tête résidents sur CUDA/hybride. Banques fixes complètes : graphe de token entier ; cache ou placement partiel : segments avec admission sur hôte et repli routé. Contexte maximal 8 192, SIMD CPU AVX2/AVX512 et backbone compatible dans le budget requis. Métadonnée explicite sur le mode et la résidence complète. Désactivé par défaut. |
| `RBITNET_CUDA_GPT_FULL_GRAPH=0` | Désactive la capture du pipeline GPT-OSS ; les mêmes noyaux et les mêmes buffers restent sur GPU. |
| `RBITNET_CUDA_GPT_SEGMENTED=1` | Force les segments pour l'ablation avec banques fixes. Cache dynamique et placement partiel sélectionnent ce mode automatiquement ; les IDs/probabilités retournent par couche et les leases protègent les pointeurs jusqu'à la fin du FFN. |
| `RBITNET_CUDA_GPT_PREFILL=1` | Préremplissage GPT-OSS causal par blocs de 1 à 32 positions, avec banques fixes entièrement résidentes. Projections quantifiées par lancement, FFN regroupés par expert et ordre final du routeur conservé. Les segments/cache/placements partiels gardent leur chemin sériel. `RBITNET_REQUIRE_GPT_PREFILL=1` refuse un chemin indisponible. |
| `RBITNET_CUDA_GPT_PREFILL_TOKENS=16` | Capacité du bloc GPT, bornée à 32. Workspaces, logits optionnels par position et scratch sont réservés avant génération. La variante `RBITNET_CUDA_GPT_PREFILL_TILE=1` conserve les octets MXFP4 mais reste expérimentale ; comparer les configurations dans le rapport dédié. |
| `RBITNET_CUDA_MOE_FUSED=1` | Fusion optionnelle du FFN résident de décodage : gate/up/biais/activation, puis down/biais/somme routée. Même réduction numérique et aucun nouveau format quantifié ; les formats gate/up distincts gardent leurs projections séparées. Les FFN de préremplissage GPT regroupés ont un chemin distinct. Aucun gain général ne justifie l'activation par défaut. |
| `RBITNET_REQUIRE_GPT_FULL=1` | Refuse un pipeline GPT résident indisponible ou un backbone/état hors budget. Cette option expérimentale accepte le repli FFN du mode segmenté ; elle ne garantit pas que toutes les banques sont sur GPU. Une ancienne DLL compatible conserve son graphe fixe mais peut ne pas fournir les snapshots ; sans exigence, une ABI segmentée absente conserve le chemin partiel réel. |
| `RBITNET_CUDA_MLA_FULL=1` | Backbone GLM/MLA, routeur, FFN partagé et tête résidents sur CUDA/hybride ; une seule copie du latent normalisé et de la clé RoPE par position. Admission des experts sur hôte, leases fixes/dynamiques et repli CPU du seul FFN routé. Projections sans biais, moins de 128 experts, contexte <=8192 et SIMD CPU AVX2/AVX512 requis. |
| `RBITNET_CUDA_MLA_FULL_GRAPH=0` | Exécution eager des mêmes segments MLA ; graphes stables par défaut. |
| `RBITNET_REQUIRE_MLA_FULL=1` | Refuse un pipeline MLA incompatible, une ancienne DLL ou un budget insuffisant pour son backbone/état ; sinon le chemin partiel reste disponible. |
| `RBITNET_CUDA_QWEN_PREFILL=1` | Préremplissage dense par blocs jusqu'à 128 tokens, limité par `RBITNET_PREFILL_CHUNK_TOKENS`. Projections matricielles partagées, convolution causale, scan GDN avec l'état conservé dans les registres, attention causale et FFN. Une synchronisation par bloc et sortie du dernier token seulement. Les checkpoints exacts interrompent les blocs aux frontières voulues ; une ancienne DLL ou un workspace indisponible garde le pipeline GPU sériel. |
| `RBITNET_REQUIRE_QWEN_FULL=1` | Refuse le chargement si le pipeline complet demandé est indisponible. Sans cette exigence, une ancienne DLL, un modèle MoE, `hybrid`, un contexte trop grand, un debug partiel ou des poids non résidents conservent le chemin antérieur et sa métadonnée de placement. |
| `RBITNET_CUDA_SPLIT_KV=1` | Attention exacte par tuiles de 256 positions dans Llama résident, Qwen dense complet, GPT-OSS complet et MLA résident. Softmax partiels puis fusion stable max/somme/numérateur, avec le dénominateur des sinks GPT-OSS, sans éviction de tokens ni quantification. Scratch et grilles stables pour les graphes ; option lue lors de la création du contexte natif. Désactivée par défaut. |

Sans le plafond commun, le budget des experts est plafonné par `RBITNET_HYBRID_MAX_VRAM_MB` moins les poids non experts déjà résidents. Ce budget de poids ne compte pas le KV actif, les snapshots, les normes/biais et le scratch natif. Avec `RBITNET_CUDA_DEVICE_BUDGET_MB`, ces allocations sont toutes comptées par un allocateur partagé. GPT-OSS/GLM retirent une réservation conservatrice des états avant le placement ; le cache utilise ensuite le solde disponible pour les poids. Les matrices d'experts gardent un miroir RAM de leurs octets quantifiés.

Les jauges `rbitnet_core_cuda_managed_{live,peak,limit}_bytes` et `rbitnet_core_cuda_managed_category_bytes` comptent les allocations possédées, sans doubler les vues partagées ni les leases. Le scratch par thread peut rester après déchargement et reste compté. Les allocations internes du driver, des bibliothèques et des graphes sont exclues ; une marge libre les sépare du budget géré. Ces jauges ne remplacent pas une mesure de toute la VRAM du processus. Une ancienne DLL n'honore pas cette nouvelle option et refuse le CUDA demandé avec ce plafond.

Les experts utilisés sont protégés par des leases jusqu'à la fin du FFN. Une table d'adresses device stable permet aux graphes de lire les allocations actuelles après éviction ou réutilisation d'un slot. Si une sélection ne tient pas dans le budget, le FFN entier passe sur CPU, dans l'ordre du routeur. Un cache trop petit peut multiplier les transferts et ralentir la génération.

Les snapshots appartiennent au runtime : poids, tokenizer, configuration RoPE et layout ne changent pas pendant sa durée de vie. Un autre chargement de modèle crée un autre cache. Ils ne sont pas persistés sur disque. Une ancienne DLL sans API de snapshot garde le repli hôte Llama ou désactive la réutilisation Qwen ; une DLL sans GEMM garde le préremplissage résident token par token.

Le compteur `rbitnet_core_gpu_split_attention_queries_total` mesure les positions exécutées, sommées sur les couches réellement configurées avec les nouveaux noyaux. Le CLI interroge le contexte natif ; un flag demandé avec une ancienne DLL ne produit pas de faux compteur. Le scratch split-KV est supplémentaire au KV actif et au budget des snapshots. Llama réserve le scratch de décodage à la création et celui des blocs au premier prefill/vérification, puis conserve leurs adresses. Qwen réserve un scratch par bloc d'attention complète. Cette option conserve la représentation F32 du cache, dense ou latente MLA ; elle ne termine pas les tickets de pages, quantification ou batching.

## Mesurer et reproduire

Les [preuves de capacité et tokenizer](benchmarks/2026-10-04-context-tokenizer/README.md) distinguent le contexte GGUF de la capacité allouée et refusent les requêtes trop longues avant SSE. Le tokenizer immuable est partagé entre comptage et génération ; Mistral SentencePiece est confronté au processeur original et au JSON HF sur les mêmes IDs, sur CPU/CUDA et serveur réel. Ces corrections ne constituent pas un forward multi-séquences.

Le placement quantifié partagé et le cache d'experts de GPT-OSS/MLA gardent désormais des vues du GGUF mappé pour leurs grands poids, avec propriétaire `Arc` conservé pendant les copies et calculs. Les matrices créées depuis des buffers autonomes conservent ce mode de stockage. Une vue/clône active interdit le remplissage du même propriétaire CUDA ; les leases de groupes protègent aussi les victimes du cache. Les octets GGUF et le format quantifié restent identiques. Les pages du fichier mappé peuvent toujours compter dans le RSS : il faut mesurer la RAM physique, pas assimiler un mmap à zéro RAM.

`/metrics` expose `rbitnet_moe_layer_*` avec `model_id`, nom GGUF, architecture et couche : hits/misses, évictions de la couche victime, octets/temps de chargement, attente du verrou, refus de capacité, groupes/octets prêts, nombres et temps de FFN GPU/repli, décisions CPU/GPU. Le registre garde seulement des références faibles aux modèles. Les gauges READY tombent à zéro lorsque le cache disparaît, même si une lease externe conserve encore des allocations physiques ; le registre CUDA mesure ces dernières séparément. Les graphes de token entier comptent les FFN GPU sans inventer de durée par couche : utiliser les compteurs `timed_*` avec les sommes de temps.

Le sélecteur `adaptive` calibre deux observations CPU puis deux GPU lorsque les groupes tiennent, et re-sonde toutes les 128 décisions par couche. Il estime le coût du calcul GPU à partir du temps FFN moins le temps des chargements réels, puis ajoute les octets manquants multipliés par le coût de copie observé. Les durées nulles/incohérentes ne calibrent pas le modèle. Un refus de capacité garde le repli CPU ; les erreurs de CUDA restent des erreurs explicites. Le mode `cache` reste le défaut : les ablations publiées ne justifient pas d'activer le sélecteur partout.

Les [mesures du placement MoE et des poids mappés](benchmarks/2026-10-03-moe-placement/README.md) comparent les politiques et le binaire précédent sur les mêmes requêtes, avec un plafond géré de 12 Gio. Le pic RSS passe de 21,28 à 10,87 Gio pour GPT-OSS et de 28,54 à 17,07 Gio pour GLM, soit des réductions de 48,9 % et 40,2 %. Le décodage reste proche du binaire précédent ; cette baisse de RAM ne démontre pas un gain de vitesse. Le sélecteur adaptatif et le cache de 8 Gio régressent dans plusieurs cas. Les 265 tests workspace, cinq suites numériques sur les vrais modèles, quatre suites serveur et douze ablations sont publiés avec leurs limites et données brutes. Ce corpus contient 24 notes communes, contre 72 dans les rapports précédents.

Les [mesures et preuves du 3 octobre 2026](benchmarks/2026-10-03-cache-foundation/README.md) publient les réponses brutes, les tests GPU/CPU, les limites du pilote MoE et les statistiques des ablations finales.

Les [ablations d'attention partitionnée et comparatifs remesurés](benchmarks/2026-10-03-split-kv/README.md) montrent un décodage long Llama de 85,9 à 377,0 tok/s et Qwen de 100,8 à 233,2 tok/s sur cette machine. Le comparatif des trois moteurs conserve un écart majeur de préremplissage froid et de latence totale ; les résultats courts, la qualité, les empreintes et les différences de capacités de contexte/KV sont publiés avec les mesures.

Les [projections Tensor Cores compensées](benchmarks/2026-10-03-tensorcore-prefill/README.md) réduisent ensuite le préremplissage Llama de 1 512,5 à 923,5 ms dans l'ablation. Les logits et la log-vraisemblance sont confrontés au chemin SIMT sur 48 positions ; les petites matrices restent SIMT. Les nouveaux comparatifs conservent un écart de latence totale face à Ollama et llama.cpp. Le compteur `rbitnet_core_gpu_tensor_gemm_calls_total` interroge les lancements natifs exécutés avec succès ; la configuration explicite du contexte évite une divergence entre les environnements Rust et CRT de la DLL Windows.

Le [préremplissage Qwen par blocs](benchmarks/2026-10-03-qwen-block-prefill/README.md) abaisse le préremplissage long de 5 262 à 808,5 ms dans l'ablation, et à 5 ms au checkpoint chaud. Les 36 réponses/12 paires SSE et 384 positions avec tokens imposés sont vérifiées ; l'annulation pendant un bloc est aussi testée. Le nouveau comparatif court mesure 258,1 tok/s Rbitnet / 215,7 Ollama / 230,5 llama.cpp ; HTTP long reste à 1 343,5 / 714,6 / 674,2 ms. Les fixtures numériques bornées et leurs échecs initiaux sont publiés ; aucune précision universelle ou supériorité générale n'est revendiquée.

Le [pipeline GPT-OSS pour les banques fixes](benchmarks/2026-10-03-gpt-full/README.md) passe de 39,1 à 90,6 tok/s dans l'ablation longue avec split-KV ; le préremplissage reste sériel, 31,4 → 14,9 s. Les 27 réponses/neuf paires SSE, 72 positions avec tokens imposés et 18 générations sont confrontées au chemin partiel. L'échec initial dû aux experts presque ex aequo et sa correction sont publiés ; le comparatif garde un retard sur Ollama/llama.cpp. Le [chemin segmenté et ses nouvelles preuves](benchmarks/2026-10-03-gpt-segmented/README.md) ajoutent cache MoE dynamique, placement partiel et snapshots GPT. Sa propre ablation finale mesure 38,88 → 80,84 tok/s avec segments/Split-KV et 31,35 → 16,66 s de préremplissage, puis 74 ms au préfixe chaud. Le cache de 8 Gio ralentit ce chemin à 67,89 tok/s et reste désactivé par défaut. Les segments coûtent de l'admission sur hôte ; le graphe entier reste choisi lorsque les banques fixes tiennent. Les 81 demandes mesurées, 27 paires SSE et neuf arrêts concordent ; aucune nouvelle parité avec les moteurs de référence n'est annoncée.

Le [préremplissage GPT-OSS par blocs](benchmarks/2026-10-04-gpt-block/README.md) réduit le préremplissage long de 5 605,5 à 1 926,5 ms et HTTP de 7 026,1 à 3 350,1 ms sur 24 notes communes, avec banques fixes et blocs ordonnés de 32 tokens. Le décodage reste proche de 90 tok/s. La version intégrée conserve 36 observations, 12 paires SSE et quatre arrêts exacts ; une trace Nsight confirme les projections multi-tokens et FFN regroupés. Les 120 positions observées et 60 générations/replays concordent avec le pipeline sériel sur le corpus borné. La fusion FFN et le tuilage MXFP4 restent optionnels : ils n'apportent pas de gain général dans cette ablation. Les blocs des segments/cache GPT et de MLA restent à intégrer.

Le [backbone MLA résident et son attention partitionnée](benchmarks/2026-10-03-mla-full/README.md) portent le décodage GLM long de 6,54 à 22,22 tok/s sur un plafond géré de 12 Gio ; le préremplissage sériel passe de 164,43 à 69,55 s. Le préfixe chaud le réduit à 313,5 ms. Ces ablations conservent 30 couches routées sur GPU et 16 en repli CPU. Le cache d'experts de 8 Gio ralentit ce corpus malgré 86,67 % de hits : 20,60 tok/s et 114,85 s de préremplissage. Il reste désactivé par défaut. Les données brutes, 72 réponses, 24 paires SSE, transferts logiques et limites sont publiés ; ce lot n'établit pas une parité avec Ollama/llama.cpp.

`scripts/benchmark_cache_stack.py` compare les modes sur le même binaire et la même DLL. Il conserve requêtes/réponses, chauffe, répétitions, temps de préremplissage/décodage, latence HTTP, compteurs, empreintes et mémoire. Il vérifie les réponses SSE en glouton, sampling avec seed et pénalités, ainsi qu'un arrêt explicite. Les séquences de référence et les tests de snapshots vérifient séparément l'annulation puis la reprise.

```powershell
python scripts/benchmark_cache_stack.py --config docs/benchmarks/2026-10-03-parity-round2/manifest.json --model llama32-1b --backend gpu --binary target/release/rbitnet.exe --library target/performance-cache/cuda-final/rbitnet_cuda_quant64.dll --output-dir target/performance-cache/llama-http
python scripts/simulate_expert_cache.py chemin/trace.jsonl --budgets-mib 512 2048 4096 8192 --output target/replay.json
python scripts/test_simulate_expert_cache.py
```

Le simulateur utilise les mêmes experts sélectionnés pour toutes les politiques et protège les groupes déjà acquis dans la couche. Il simule le placement et les octets transférés ; il ne prédit pas les tok/s ni le recouvrement CPU/GPU. `--events N` permet de vérifier un segment contre les compteurs d'une exécution réelle.

## Correctness des transferts

Les graphes natifs utilisent des flux CUDA privés non bloquants. Une copie H2D depuis la RAM pageable peut rendre la main après staging, avant la fin du DMA, selon la [sémantique CUDA](https://docs.nvidia.com/cuda/cuda-runtime-api/api-sync-behavior.html). Le runtime attend donc la fin des chargements et des refills avant de publier leurs pointeurs. Les normes et biais natifs sont chargés et synchronisés sur le flux de leur contexte. Cela fixe la dépendance de transfert ; le préchargement asynchrone devra ensuite remplacer cette attente par des événements explicites.

## Étapes suivantes

Le cache à la demande ne termine pas [#84](https://github.com/azerothl/Rbitnet/issues/84) et [#86](https://github.com/azerothl/Rbitnet/issues/86) : le choix CPU/GPU par coût fonctionne pour un FFN routé complet, mais le préchargement épinglé avec recouvrement mesuré et l'exécution mixte par expert restent à intégrer. Le pipeline Qwen dense dispose de snapshots K/V device associés aux checkpoints GDN/convolution ; la réutilisation reste exacte au checkpoint. GLM dispose du backbone MLA résident, d'une admission d'experts par segments et de préfixes compressés. GPT-OSS dispose des graphes fixes et des segments pour cache/placement partiel, avec préfixes immuables. Le préremplissage par blocs des segments/cache GPT et du pipeline MLA, le KV device paginé/quantifié, la persistance des sessions et les forwards multi-séquences restent dans leurs tickets [#88–#96](https://github.com/azerothl/Rbitnet/issues/98).

Le prefill Llama ordinaire retourne les logits du dernier token. La nouvelle API de vérification retourne un résultat par position et permet la correction/rollback d'un draft de tokens PLD. Les [mesures spéculatives](benchmarks/2026-10-03-speculative-llama/README.md) justifient de garder `RBITNET_SPECULATIVE_PLD` désactivé par défaut : un gain sur une réponse répétitive courte ne compense pas les régressions des autres prompts. Le draft GGUF et Qwen restent ouverts dans [#97](https://github.com/azerothl/Rbitnet/issues/97).
